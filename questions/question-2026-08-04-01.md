# 想定問題 2026-08-04-01

- **判断軸**: 比例性（対処が問題の規模に見合うか）
- **対応ドメイン**: Domain 3 — Claude Code Configuration & Workflows（配点 20%）／タスクステートメント 3.1（階層・スコープを踏まえた設定）
- **出典英文**: 「When to use each scope」（Claude Code Docs・Settings ページ）
- **出典URL**: https://code.claude.com/docs/en/settings

---

## Scenario

Your team of eight developers shares a repository with `.claude/settings.json` committed to version control. One developer adds a machine-specific path to their local toolchain in that file so Claude Code can locate a custom linter. After the next pull, five developers report that Claude Code fails to run the linter, and two have started disabling the hook entirely to unblock their work.

## Question

What is the most effective first step to resolve this?

## Options

**A.** Move the machine-specific path to `.claude/settings.local.json` on each developer's machine, keeping the shared settings in the committed file.

**B.** Remove the linter hook from the project configuration and have each developer configure it independently in their user scope.

**C.** Add conditional logic to the shared settings file that detects each developer's operating system and selects the appropriate path.

**D.** Require all developers to install the linter at an identical absolute path so the committed configuration works uniformly.

---

## 解答

<details>
<summary>正解と解説を開く</summary>

**正解**: A

本文が明示するとおり、Local スコープは `Machine-specific settings that won't work for others` のためのものである。マシン固有のパスは定義上 Project スコープに置くべきものではなく、**置き場所を間違えたことが根本原因**。共有すべき設定（リンター実行の仕組み自体）は Project に残し、各自の環境に依存する部分だけを Local へ移すのが、問題の規模に見合った最小の修正になる。Local は Claude Code が書き込む際に自動で gitignore されるため、再発も防げる。

**誤答の理由**

- **B** は過剰。リンター実行の仕組み自体はチーム全員が持つべきもの（`Plugins the whole team should have`）であり、Project スコープに置く価値がある。全体を各自の裁量に委ねると、本来標準化したかったツール環境（`Standardizing tooling across collaborators`）が崩れる。
- **C** は最も過剰設計。設定ファイルに条件分岐を持ち込むと保守負担が継続的に発生する。スコープを正しく使い分ければ、そもそも分岐は不要。
- **D** は症状ではなく人間の運用に負担を転嫁している。全員に同一パスでのインストールを強制するのは非現実的で、環境の違い（OS、権限、既存構成）を無視している。

</details>

### 【全訳】

**Scenario（シナリオ）**

8人の開発者からなるあなたのチームは、バージョン管理にコミットされた `.claude/settings.json` を含むリポジトリを共有しています。ある開発者が、Claude Code がカスタムリンターを見つけられるように、そのファイルへ自分のローカル環境のツールチェーンを指すマシン固有のパスを追加しました。次の pull の後、5人の開発者から Claude Code がリンターの実行に失敗するという報告が上がり、2人は作業の停滞を解消するためにフックを完全に無効化し始めてしまいました。

**Question（設問）**

これを解決するための、最も効果的な最初の一手はどれですか。

**Options（選択肢）**

A. マシン固有のパスを各開発者のマシン上の `.claude/settings.local.json` へ移し、共有設定はコミット済みのファイルに残す。

B. プロジェクト設定からリンターのフックを削除し、各開発者に自分の User スコープで個別に設定させる。

C. 各開発者の OS を検出して適切なパスを選択する条件分岐のロジックを、共有設定ファイルに追加する。

D. コミット済みの設定が一様に機能するよう、全開発者にリンターを同一の絶対パスへインストールすることを要求する。

**訳を並べて見える差分**：A だけが「置き場所を正す」修正で、共有すべきものは共有したまま、環境依存の部分だけを分離している。B は「共有をやめる」、C は「設定ファイルを複雑にする」、D は「人間に統一を強制する」。**A 以外はいずれも、標準化を放棄するか、複雑さを増やすか、運用負担を人に転嫁する**構造になっている。
