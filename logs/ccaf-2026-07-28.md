# Q&A 形式の知識カード（CCAR-F 技術知識）

## Q. Claude Code のフック（Hooks）と、CLAUDE.md やプロンプトの指示は、確実性の観点で何が違うのか？

**A. フック（Hooks）は「強制（enforcement）」、CLAUDE.md やプロンプトの指示は「希望」である。**

Claude Code のフック（Hooks）は、Claude Code のライフサイクルの要所（編集後の整形、コマンド実行前のブロック、入力要求時の通知、セッション開始時のコンテキスト注入など）でユーザー定義のコードを走らせる仕組みである。フックが走るかどうかをモデルは決められず、ハーネス（Claude Code 本体）が決める。したがって、実行前フックがブロック状態で終われば、モデルが何を意図してもツール呼び出しは阻止される。

一方、CLAUDE.md やプロンプトに「危険なコマンドを実行するな」と書いても、それは丁重な指示にすぎず、モデルが判断を誤れば破られる（確率的遵守）。

**要点：指示は希望、フックは保証。** この対比は CCAR-F の公式サンプル問題パターン①「金銭的影響など確実性が要る場面では、プロンプト強化ではなくプログラム的強制（前提条件・フック）を選ぶ」と完全に一致する。

（出典: Anthropic Academy「What you can automate」（Hooks 導入）／学習日 2026-07-28）

## Q. Claude Code の Plan サブエージェントは何をし、なぜコンテキストを別ウィンドウに分けるのか？

**A. Plan サブエージェントは、プランモードでプラン提示前のコードベース調査を担う「読み取り専用」の調査エージェントであり、探索の出力をメイン会話とは別のコンテキストウィンドウに隔離するために存在する。**

Plan サブエージェントの属性は、モデル＝メイン会話から継承、ツール＝読み取り専用のみ（Write と Edit は拒否）、目的＝プランニングのためのコードベース調査。プランモード中に Claude がコードベースを理解する必要が生じると、Claude は調査を Plan サブエージェントに委譲し、探索の大量出力を別ウィンドウに閉じ込めて、メイン会話を読み取り専用のまま保つ。

これは CCAR-F の Domain 1（Agentic Architecture & Orchestration）の 1.2（コーディネーター＝サブエージェント方式）・1.3（サブエージェントの呼び出しとコンテキスト受け渡し）・1.7（セッション状態の管理）と、Domain 5 の 5.4（大規模コードベース探索におけるコンテキスト管理）に直結する。書き込み権限を与えない「最小権限」は、調査段階で副作用を起こさないための決定論的な制約である。

（出典: Anthropic Academy「Plan」（Plan サブエージェント定義カード）／学習日 2026-07-28）

## Q. MCP サーバー設定で `url` はあるのに `type` が無いとどうなるか？ `streamable-http` とは何か？

**A. `type` が無いエントリは stdio サーバーと解釈されて設定エラーになり、Claude Code はそのサーバーをスキップして明示エラーを出す。`streamable-http` は `http` の別名（エイリアス）である。**

JSON 設定（`.mcp.json`、`~/.claude.json`、または `claude mcp add-json`）で、`type` フィールドはトランスポート種別を表し、値には `http` / `sse` / `ws` などがある。`type` を省くと Claude Code は stdio サーバーとみなすため、`url` だけのエントリはエラーになり、`MCP server "<name>" has a "url" but no "type"; add "type": "http" (or "sse" / "ws") to this entry` と報告される（v2.1.202 より前は `command: expected string, received undefined` という分かりにくい旧メッセージだった）。`streamable-http` は MCP 仕様書での正式名で、`http` の別名として受理されるため、サーバー付属ドキュメントからコピーした設定を無修正で使える。

リモート HTTP サーバーの追加コマンドは `claude mcp add --transport http <name> <url>`。Bearer 認証は `--header "Authorization: Bearer <token>"` で付ける。CCAR-F の Domain 2（Tool Design & MCP Integration）2.4（MCP サーバーの統合）。「誤設定を握りつぶさず、修正法まで添えて明示エラーを返す」設計は Domain 2 の構造化エラー思想（2.2）とも通じる。

（出典: Anthropic Academy「Installing MCP servers」／学習日 2026-07-28）

## Q. Claude Code のスキルは、どの範囲で、どの手段で共有・配布するのか？

**A. 個人（`~/.claude/skills/`）→ チーム（リポジトリにコミット）→ 全社（プラグイン配布・managed settings による組織展開）へと、スコープを段階的に広げて共有する。**

スキル共有の3段階は、(1) リポジトリへコミットしてチームで版管理、(2) プラグイン経由で配布して横展開、(3) managed settings（管理者が集中管理する設定）で全社展開、という規模の階段になっている。個人スキルフォルダは全プロジェクトで使える。

これは CCAR-F の Domain 3（Claude Code Configuration & Workflows）3.2（スキルの作成・設定）に対応し、規模に比例して手段を選ぶという公式サンプル問題パターン③（過剰設計を避け、原因・規模に比例した最小の対処を選ぶ）と同じ判断軸で問われうる。個人利用に全社設定を持ち出すのは過剰、全社統制にローカル設定は不足、という向きで正誤が分かれる。

（出典: Anthropic Academy 次レッスン予告（スキル共有）／学習日 2026-07-28）

# Q&A 形式の知識カード（学習法・ソース判定）

## Q. 英文のソース区分（Anthropic Academy か Claude Code Docs か）は、何を基準に判定すべきか？

**A. 「主題（トピック）」ではなく「文章の種類（レジスター／語り口）」で判定する。話題が Claude Code でも、Claude Code Docs とは限らない。**

Claude Code というテーマは、リファレンス文書（Claude Code Docs）と講座教材（Anthropic Academy）の両方に登場する。したがって「Claude Code の話だから Claude Code Docs」と主題で決めると誤る。判定は地の文の語り口で行う。`lesson` / `In this lesson` / `In the next lesson` / `you'll learn` / `you'll build` / `By the end of ...` のようなレッスン・二人称の学習ナレーションがあれば Anthropic Academy。`Option 1/2`・構文見出し・厳密なエラー文字列・バージョン注記などはリファレンス／タスク指向の Claude Code Docs のサインだが、これらは Academy 教材にも埋め込まれうる。両方の要素があるときは、レッスン的な語りを優先して Academy と判定する。

この区分は english-parsing スキルの出力に直結する。english-parsing では、ソース区分が Anthropic Academy のときだけ【7. ソース情報】ブロック（公式ドキュメントへのディープリンク）を出力する。ゆえにソースを誤ると【7】が丸ごと脱落する。本日、この原則を english-parsing スキル v3.9 として明文化した。

## Q. Claude Code の「個人スキル（`~/.claude/skills/`）」と、claude.ai チャット環境で編集しているスキルは同じものか？

**A. 別物である。個人スキルはユーザーのマシン上で `claude` CLI が読むもの。チャット環境のスキル（`/mnt/skills/user/` など）はサンドボックス側にあり、ユーザーのホームディレクトリには書き込めない。**

Claude Code の個人スキルは、ディレクトリ名がそのままコマンドになる（例：`summarize-changes/` → `/summarize-changes`）。frontmatter は `description` だけでも動き、`name` があっても表示ラベルにしかならない。SKILL.md 内の `!` `git diff HEAD` のような行は **dynamic context injection（動的コンテキスト注入）**で、Claude Code がコマンドを実行し、モデルが本文を読む前にその出力を差し込む。これにより応答が推測ではなく実際の作業ツリーに接地する。この「事実に接地させる」発想は、CCAR-F の Domain 5（コンテキスト管理と信頼性）とも通じる。

（出典: 学習中の質疑応答 ／学習日 2026-07-28）

## 今日の型に関する気づき

**VP8（動詞型8：主語＋他動詞＋疑問詞＋to不定詞、人を取らない）と VP20（動詞型20：主語＋他動詞＋人＋疑問詞＋to不定詞、人を取る）の識別法**：`decide when to load`（VP8）は動詞と疑問詞の間に人が入らない。`tells Claude when to use`（VP20）は動詞の直後に人（Claude）が入る。**疑問詞＋to不定詞の前に「人」の目的語があるか**で見分ける。

**VP18B（使役 let＋原形）と VP7A（need＋to不定詞）の対比**：`let you run`（let は to なしの原形）と `needs to understand`（need は to つき）。使役 let/make/have は原形、need/want は to 不定詞、という基本パターンを同じ日にまとめて確認できた。

**VP6E（need＋動名詞＝受身の意味）**：`tests that need updating` は「更新される必要があるテスト」。need＋-ing が受身を表す語法。TOEIC でも問われる。

## 累積頻度について

**本日分のみ記録。累積表は捏造しない。** 累積出現回数を正しく更新するには、前日までの `ccaf-YYYY-MM-DD.md`（または累積表）が必要だが、本日の会話には貼られていない。翌日の会話冒頭に直近のファイルを貼れば、累積を途切れさせずに更新できる。

**要注意（未出現の型）**：完了時制（現在完了 [5] など）と AP1A〜AP1E（形容詞＋to不定詞）は、本日の技術文書では出現しなかった。TOEIC では頻出のため、Hornby の原典例文（Jim is easy to please. など）で別途補強する。
