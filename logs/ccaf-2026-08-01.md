# Q&A 形式の知識カード（CCAR-F 技術知識）

## Q. スキルをチーム・組織で共有する3つの方法と、それぞれが向く場面は？

**A. リポジトリへのコミット（チーム）、プラグインとマーケットプレイス（プロジェクト横断・コミュニティ）、エンタープライズ managed settings（組織全体）の3段階。スコープが広がる順に並ぶ。**

学習目標リストが挙げた4項目は、(1) Git リポジトリにコミットしてチームと共有、(2) プラグインとマーケットプレイスでプロジェクト横断的に配布、(3) エンタープライズの managed settings で組織全体へ展開、(4) カスタムサブエージェントが特定のスキルを使うよう設定、である。(1)〜(3) は配布スコープの階段だが、(4) は別の軸で、サブエージェントごとに使えるスキルを限定する話。

CCAR-F では Domain 3（3.1 設定の階層とスコープ／3.2 スキル・プラグインの作成）が主。(4) は Domain 1（1.2〜1.3 サブエージェントの構成とコンテキスト受け渡し）に接続する。判断軸は③規模に比例した手段選択（個人利用に全社設定は過剰、全社統制にローカル設定は不足）。

（出典: Anthropic Academy 学習目標リスト／学習日 2026-08-01）

## Q. サブエージェントはスキルを継承するか？

**A. 継承しない。使わせたいスキルは明示的に設定する必要がある。**

動画紹介の英文が `an important gotcha: subagents don't inherit skills automatically` と名指しした点。**サブエージェントは親の会話からスキルを自動で引き継がない**ため、明示設定が要る。

自動継承しない理由は、コンテキストの肥大と意図しない能力付与を防ぐためと考えられる。サブエージェントは「別のコンテキストウィンドウで動く、役割を限定したエージェント」なので、親の持ち物をすべて引き継ぐとその利点が失われる。先に読んだ Plan サブエージェント（読み取り専用ツールのみ、Write と Edit は拒否）と同じ思想の帰結である。

`gotcha`（落とし穴・引っかかりやすい罠。"I've got you" の口語的縮約）として公式に名指しされたものは出題されやすい。「サブエージェントがスキルを使えないのはなぜか」というトラブルシュート型で問われうる。CCAR-F の Domain 1（1.2／1.3）。

（出典: Anthropic Academy 動画紹介／学習日 2026-08-01）

## Q. standalone 構成とプラグイン、どちらをいつ使うか？

**A. 個人の試作・単一プロジェクトなら standalone（`.claude/`）、共有・複数プロジェクト・バージョン管理が要るならプラグイン。まず standalone で素早く反復し、共有の準備ができたらプラグインへ変換する。**

| 方式 | スキル名 | 向く場面 |
|---|---|---|
| Standalone（`.claude/` ディレクトリ） | `/hello` | 個人的なワークフロー、プロジェクト固有のカスタマイズ、素早い実験 |
| プラグイン（`.claude-plugin/plugin.json` を持つディレクトリ） | `/plugin-name:hello` | チームメイトとの共有、コミュニティへの配布、バージョン管理されたリリース、プロジェクト横断での再利用 |

**プラグインの判別条件は `.claude-plugin/plugin.json` の存在**である。`.claude/`（standalone）と `.claude-plugin/`（プラグイン）は名前が似ているが別物。

**名前空間はトレードオフ**：standalone なら `/hello` と短いが、プラグインは `/plugin-name:hello` と長くなる。ただし `namespacing prevents conflicts between plugins`（名前空間はプラグイン間の衝突を防ぐ）。複数プラグインを入れる前提なら必須。

公式は `Start with standalone configuration in .claude/ for quick iteration, then convert to a plugin when you're ready to share.` と段階的移行を推奨する。**最初から作り込まない**という設計思想で、CCAR-F の判断軸③（規模に比例した手段）と一致する。

（出典: Claude Code Docs「When to use plugins vs standalone configuration」／学習日 2026-08-01）

## Q. Claude Code の設定スコープ4種と、それぞれの場所・影響範囲は？

**A. Managed → User → Project → Local の4層。上から影響範囲が狭くなる。**

| スコープ | 場所 | 誰に影響するか | チーム共有 |
|---|---|---|---|
| **Managed** | サーバー管理設定、plist / レジストリ、システムレベルの `managed-settings.json` | サーバー管理配布＝組織の全メンバー／plist・HKLM レジストリ・ファイル配布＝そのマシンの全ユーザー／**HKCU レジストリ配布＝現在のユーザーのみ** | はい（IT が配備） |
| **User** | `~/.claude/` ディレクトリ | あなた自身、**全プロジェクトにわたって** | いいえ |
| **Project** | リポジトリ内の `.claude/` | このリポジトリの全協力者 | はい（git にコミット） |
| **Local** | `.claude/settings.local.json` | あなた自身、**このリポジトリ内でのみ** | いいえ（gitignore される） |

**要点3つ**：
1. **User と Project の違いはパスの `~`**。`~/.claude/`（ホーム＝全プロジェクトに効く）と `.claude/`（リポジトリ内＝そのプロジェクトのみ）。文字面は似ているが適用範囲が根本的に違う。
2. **同じ Managed でも配布経路で影響範囲が変わる**。HKLM（マシン全体）と HKCU（現在のユーザーのみ）の違いは Windows 環境での設計に効く。
3. **Local は自動で gitignored される**。Claude Code が設定を書き込む際に `.gitignore` へ登録し、うっかり個人設定をコミットする事故を防ぐ。「確実性が要る場面は機構で担保する」思想の一例。

CCAR-F の Domain 3（3.1 設定の階層とスコープ）の中核。「チーム全員に効かせたい／自分だけ・このリポジトリだけ／組織全体に強制したい」という要件から**どのスコープに置くか**を選ばせる形で問われやすい。

（出典: Claude Code Docs「Available scopes」／学習日 2026-08-01）

## Q. Agent Skills とは何か。プロンプトとどう違うか？

**A. スキルは「再利用可能でファイルシステムに基づくリソース」。プロンプト（一回限りの会話レベルの指示）と違い、必要時に読み込まれ、会話をまたいで同じ指示を繰り返す必要をなくす。**

定義文は `Skills are reusable, filesystem-based resources that provide Claude with domain-specific expertise: workflows, context, and best practices that transform general-purpose agents into specialists.`

**プロンプトとの本質的な差**：`Unlike prompts (conversation-level instructions for one-off tasks)` が核心。プロンプトは会話に閉じた一回限りの指示で、会話が終われば消える。スキルは**ファイルシステム上に永続**し、複数の会話をまたいで効く。この差が `eliminate the need to repeatedly provide the same guidance` という利点に直結する。

**3つの利点**：(1) Claude を専門化する（領域固有のタスク向けに機能を仕立てる）、(2) 反復を減らす（一度作れば自動的に使われる）、(3) 機能を組み合わせる（スキルを組み合わせて複雑なワークフローを構築）。

`Skills load on-demand`（必要に応じて読み込まれる）は段階的開示と同じ思想で、常時コンテキストを占有しない。

CCAR-F では Domain 3（3.2）が主。ただし**プロンプトとの対比**が明示されているため Domain 4（Prompt Engineering）にも接点がある。「毎回同じ指示を貼っている状況をどう改善するか」→スキル化、という使い分けで問われうる。

（出典: Claude Platform Docs「Agent Skills overview」／学習日 2026-08-01）

## Q. プラグインを作る最小手順は？ `--plugin-dir` は何のためか？

**A. マニフェスト（`.claude-plugin/plugin.json`）を作る → スキルを追加する → `--plugin-dir` フラグでローカルテストする、の3段階。**

Quickstart の英文は `You'll create a manifest (the configuration file that defines your plugin), add a skill, and test it locally using the --plugin-dir flag.` と手順を予告する。

**`--plugin-dir` の意義**：マーケットプレイスへ公開したり `/plugin install` で導入したりする前に、**手元のディレクトリを直接指定して動作確認できる**。開発と配布を分離する設計で、試行錯誤の段階でリポジトリを汚さずに済む。

なお `--plugin-dir` は公式 Exam Guide §17 Appendix の CLI 一覧（`-p` / `--print` / `--output-format json` / `--json-schema`）に**含まれていない**ため、フラグ名そのものが問われる可能性は低い。

（出典: Claude Code Docs「Quickstart」／学習日 2026-08-01）

## Q. ソース区分（Anthropic Academy か Claude Code Docs か）は何で判定すべきか？

**A. 「学習単位への言及」があるときだけ Academy と判定する。二人称ナレーションだけでは判定できない。**

本日、判定基準を作り直すことになった。

**第1の誤り（過去に修正済み・v3.9）**：「Claude Code の話だから Claude Code Docs」と**主題**で判定した。同じ話題が公式ドキュメントにも Academy 教材にも登場するため誤る。

**第2の誤り（本日発覚・v10.1 で修正）**：v3.9 で「レジスター（語り口）で判定する」方針にした際、Academy のサインとして `you'll learn` などの**二人称ナレーション**を挙げた。しかしこれが粗すぎた。**公式ドキュメントの Quickstart や How-to ガイドも二人称で書かれる**。実際 `This quickstart walks you through ... You'll create a manifest ...` は Claude Code Docs の記述だが、これを Academy と誤判定した。

**現在の基準（v10.1）**：
- **Academy と判定するのは、学習単位への言及がある場合に限る** — `lesson` / `course` / `module` / `In the next lesson` / `By the end of this lesson` / 動画への言及など、**コースの構造を示す語**。
- **二人称は判定材料にしない** — `you'll create` / `This guide walks you through ...` は Docs でも普通に使われる。
- **Docs 寄りのサイン** — `Quickstart` / `How to` / `Reference` / `Overview` という見出し語、CLI フラグ・ファイルパス・設定キーの仕様記述、バージョン注記、`Option 1 / 2` の選択肢提示、パラメータ表。
- **迷ったら Docs** — 誤って Academy とすると【7】【9】が余計に出るが、逆は省略されるだけで実害が小さい。

この判定は english-parsing の【7】🔗ソース情報と【9】公式スキル推奨の出力可否に直結するため、誤ると余計なブロックが出る。

（出典: 学習中の質疑応答（2026-08-01 のソース区分訂正）／学習日 2026-08-01）

## 今日の型に関する気づき

**VP8 と VP10 の識別（本日最大の学習点）**：同じ動詞でも、後続が **to不定詞**なら VP8（`learn how to share`＝無時制）、**主語＋動詞を持つ定形節**なら VP10（`learn which approach fits which scenario`＝fits が現在形）。動画紹介の英文では**1つの文の中で2つの型が and で並列**されていた（`You'll learn which approach fits which scenario and how to handle an important gotcha`）。**後続が時制を持つかどうか**が判別の決め手。

**VP17A の意味上の主語**：`Configure custom subagents to use specific skills` の to 不定詞の意味上の主語は**目的語（subagents）**であり、文の主語ではない。「サブエージェントがスキルを使う」という関係。取り違えると「スキルを使うために設定する」と目的の不定詞に誤読する。

**load の中間態的用法**：`Skills load on-demand` は能動態だが「読み込まれる」という受動の意味。`The book sells well.` と同型で、技術英語では `are loaded` と書かずに能動で表すのが慣用。

**affect は他動詞**：`Who it affects`（列名）。日本語の「〜に影響する」に引きずられて `affect to` としない。名詞形 effect との混同にも注意。

**比較級の強調**：`much more valuable`。very は比較級を修飾できない（× very more valuable）。強調には much / far / a lot / even を使う。
