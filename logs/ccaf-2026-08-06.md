# Q&A 形式の知識カード（技術知識）

## Q. Claude Code の4つの設定スコープは、それぞれどういう用途に使うのか？

**A. Managed は組織が強制するもの、User は自分がどこでも使うもの、Project はチーム全員が持つべきもの、Local は自分のこの環境だけのもの。**

| スコープ | 用途（本文の3項目） |
|---|---|
| **Managed** | ①組織全体で強制されねばならないセキュリティポリシー ②上書きできないコンプライアンス要件 ③IT／DevOps が配備する標準化された設定 |
| **User** | ①どこでも使いたい個人的な設定（テーマ、エディタ設定） ②全プロジェクトで使うツールやプラグイン ③API キーと認証情報（安全に保管される） |
| **Project** | ①チームで共有する設定（権限、フック、MCP サーバー） ②チーム全体が持つべきプラグイン ③協力者全体でツール環境を標準化すること |
| **Local** | ①特定のプロジェクト向けの個人的な上書き設定 ②チームと共有する前に設定をテストすること ③他の人には機能しないマシン固有の設定 |

**前節との対応**：8/1 に読んだ「Available scopes」が**場所・影響範囲・共有可否**という「何であるか」を定義したのに対し、本節は**用途**という「いつ使うか」を示す。この2節をセットで押さえると Domain 3.1 が完成する。

**User と Project の判断基準**：本文の対比が明快。`Tools and plugins you use across all projects`（全プロジェクトで使う＝User）と `Plugins the whole team should have`（チーム全体が持つべき＝Project）。**「自分がどこでも使うか」「チーム全員が持つべきか」**という軸で分かれる。

（出典: Claude Code Docs「When to use each scope」／学習日 2026-08-06）

## Q. 4つのスコープの性格の違いは、英語表現のどこに表れているか？

**A. 使われる法助動詞と態が、階層ごとに違う。上位ほど強制力が強く、下位ほど個人の裁量が大きい。**

これは本日最大の発見。**文法が設計思想を映している**例である。

| スコープ | 使われる法助動詞 | 態 | 含意 |
|---|---|---|---|
| **Managed** | `must be enforced`（義務）／`can't be overridden`（不可能） | **3項目すべて受動態** | 強制と禁止。開発者は「強制される側」 |
| **User** | （法助動詞なし。`you want` / `you use`） | 能動態 | 個人の裁量 |
| **Project** | `should have`（当為） | 能動態 | 推奨。強制ではない |
| **Local** | `won't work for others`（未来の否定） | 能動態 | 他者には合わないという事実の指摘 |

**Managed が受動態で統一されている**のが特に印象的。`must be enforced` / `can't be overridden` / `deployed by IT/DevOps` と、3項目すべてが受け身。開発者から見れば「自分では変えられないもの」であり、その立場が文法レベルで表現されている。

**見出しの `is for` と `is best for` の差**：Managed だけ `Managed scope is for:`、他3つは `is best for:`。**`best` の有無が選択の余地を示す**。Managed は組織が強制する層なので「そのためのもの（唯一の選択肢）」、他は「最も適する（相対的な推奨）」。

（出典: Claude Code Docs「When to use each scope」／学習日 2026-08-06）

## Q. Local スコープの3つ目の用途「他の人には機能しない設定」が実務上なぜ重要か？

**A. マシン固有のパスを Project に置くと、pull した他のメンバーの環境が壊れるため。Local は自動で gitignore されるので、この事故を機構的に防げる。**

原文は `Machine-specific settings that won't work for others`。

自分の環境固有のパス（カスタムツールのインストール先など）を `.claude/settings.json`（Project スコープ）に書いてコミットすると、他のメンバーが pull したときにそのパスは存在せず、設定が壊れる。

8/1 に確認したとおり、**Local（`.claude/settings.local.json`）は Claude Code が書き込む際に自動で `.gitignore` へ登録される**。つまり「共有してはいけないもの」を置く場所が、機構的に共有されないよう設計されている。「確実性が要る場面は機構で担保する」という一貫した思想の一例。

**本日の想定問題は、まさにこの事故を題材にした**（下記【想定問題】を参照）。

（出典: Claude Code Docs「When to use each scope」／学習日 2026-08-06）

# 【想定問題】全文（v10.3 形式）

本日の英文から生成した想定問題を、解説を含めて全文収録する。**同じ内容を `questions/` にも1問1ファイルで保存した**（新スキル question-archive による）。

**判断軸**: 比例性（対処が問題の規模に見合うか）
**対応ドメイン**: Domain 3 — Claude Code Configuration & Workflows（配点 20%）／タスクステートメント 3.1

## Scenario

> Your team of eight developers shares a repository with `.claude/settings.json` committed to version control. One developer adds a machine-specific path to their local toolchain in that file so Claude Code can locate a custom linter. After the next pull, five developers report that Claude Code fails to run the linter, and two have started disabling the hook entirely to unblock their work.

## Question

> What is the most effective first step to resolve this?

## Options

> **A.** Move the machine-specific path to `.claude/settings.local.json` on each developer's machine, keeping the shared settings in the committed file.
>
> **B.** Remove the linter hook from the project configuration and have each developer configure it independently in their user scope.
>
> **C.** Add conditional logic to the shared settings file that detects each developer's operating system and selects the appropriate path.
>
> **D.** Require all developers to install the linter at an identical absolute path so the committed configuration works uniformly.

## 正解と誤答の理由

**正解**: A。本文が明示するとおり、Local スコープは `Machine-specific settings that won't work for others` のためのものである。マシン固有のパスは定義上 Project スコープに置くべきものではなく、**置き場所を間違えたことが根本原因**。共有すべき設定（リンター実行の仕組み自体）は Project に残し、各自の環境に依存する部分だけを Local へ移すのが、問題の規模に見合った最小の修正になる。Local は自動で gitignore されるため、再発も防げる。

**誤答の理由**:
- **B** は過剰。リンター実行の仕組み自体はチーム全員が持つべきもの（`Plugins the whole team should have`）であり、Project スコープに置く価値がある。全体を各自の裁量に委ねると、本来標準化したかったツール環境（`Standardizing tooling across collaborators`）が崩れる。
- **C** は最も過剰設計。設定ファイルに条件分岐を持ち込むと保守負担が継続的に発生する。スコープを正しく使い分ければ、そもそも分岐は不要。
- **D** は症状ではなく人間の運用に負担を転嫁している。全員に同一パスでのインストールを強制するのは非現実的で、環境の違い（OS、権限、既存構成）を無視している。

### 【英語の型と語法】

- **動詞型 [VP6A]**（主語＋他動詞＋名詞／代名詞）
  → 該当箇所: `shares a repository` / `adds a machine-specific path` / `Move the machine-specific path` / `Remove the linter hook` / `Add conditional logic`
  → 同型の例: Everyone likes her.
  → 構文と修飾: `Your team of eight developers`(S)＋`shares`(V)＋`a repository`(O)＋`with ... committed to version control`(M・付帯状況)。**`with + 名詞 + 過去分詞`** の構文で「〜がコミットされた状態で」。

- **動詞型 [VP6C]**（主語＋他動詞＋動名詞）
  → 該当箇所: `two have started disabling the hook entirely`
  → 同型の例: She enjoys painting.
  → 構文と修飾: `two`(S＝two developers の省略)＋`have started`(V・**現在完了**)＋`disabling the hook entirely`(O＝動名詞句)＋`to unblock their work`(M・目的)。現在完了が「すでに始めてしまい今も続いている」という緊急性を作る。

- **動詞型 [VP7A]**（主語＋他動詞＋to不定詞）
  → 該当箇所: `Claude Code fails to run the linter`
  → 同型の例: I forgot to post your letter.
  → **fail to do**（〜し損なう）。単なる否定（doesn't run）ではなく「試みたが果たせない」という含意を持つ。技術文書で障害を述べる定型。

- **動詞型 [VP9]**（主語＋他動詞＋that節）
  → 該当箇所: `five developers report that Claude Code fails to run the linter`
  → 同型の例: Do you think (that) it will rain?
  → report＋that 節（事実の報告）。**VP10（間接疑問）との違い**は、that 節が確定した事実を、whether / which 節が不確定な事柄を導く点。

- **動詞型 [VP17A]**（主語＋他動詞＋名詞／代名詞＋to不定詞）
  → 該当箇所: `Require all developers to install the linter`（選択肢D）
  → 同型の例: Do you want me to stay?
  → require＋O＋to 不定詞。**to 不定詞の意味上の主語は developers**。

- **動詞型 [VP18B]**（主語＋他動詞＋名詞／代名詞＋原形不定詞）＝使役 have
  → 該当箇所: `have each developer configure it independently`（選択肢B）
  → 同型の例: Let me go!（let の場合）
  → **使役の have＋O＋原形**。to は付かない（× have him to configure）。let / make / have が同じ型を取る。

**時と時制**
- **[1] 単純現在時制**: `shares` / `adds` / `report` / `fails` / `detects` / `selects` / `works`。write の活用: He writes。
- **[5] 現在完了時制**: `have started`。write の活用: He has written。**すでに始まって今も続く**問題の緊急性を示す。
- **時制の枠外（命令形）**: 選択肢の `Move` / `Remove` / `Add` / `Require`。
- **時制の枠外（法助動詞）**: `so Claude Code can locate ~`（目的の can）。
- **時制の枠外（準動詞）**: 付帯状況 `with ... committed`；動名詞 `disabling`；目的の to 不定詞 `to unblock` / `to resolve` / `to install`；付帯状況の分詞 `keeping the shared settings`（選択肢A）。

### 【語彙・語法メモ】

- **toolchain**（名）ツールチェーン。開発に使う一連の道具立て。
- **linter**（名）リンター。コードの静的解析ツール。
- **locate**（他動）見つける・位置を特定する。
- **fail to do**（成句）〜し損なう。単なる否定より「試みて果たせない」という障害の含意が強い。
- **disable**（他動）無効化する。対義は enable。
- **unblock**（他動）（滞りを）解消する。un-＋block。IT・ビジネス文脈で頻出。

- **identical**（形）同一の。
- **absolute path**（名句）絶対パス（対義は relative path）。
- **uniformly**（副）一様に・統一的に。
- **keeping ~**（付帯状況の分詞・選択肢A）〜を残したまま。**「既存を捨てない」含意が正解のサイン**になっている。

### 【全訳】

**Scenario（シナリオ）**

**Question（設問）**
これを解決するための、最も効果的な最初の一手はどれですか。

**Options（選択肢）**

A. マシン固有のパスを各開発者のマシン上の `.claude/settings.local.json` へ移し、共有設定はコミット済みのファイルに残す。

B. プロジェクト設定からリンターのフックを削除し、各開発者に自分の User スコープで個別に設定させる。

C. 各開発者の OS を検出して適切なパスを選択する条件分岐のロジックを、共有設定ファイルに追加する。

# Hornby 型の出現記録（本日分のみ）

出典：A.S. ホーンビー『第2版 英語の型と語法』伊藤健三 訳注（オックスフォード大学出版局）

| 型番号 | 型の定義 | 該当箇所 | 出典 |
|---|---|---|---|
| **VP1** | 主語＋BE＋補語 | Managed scope **is for**:／User scope **is best for**: | 本文 |
| **VP6A** | 主語＋他動詞＋名詞 | you **want** everywhere／you **use** across all projects／the whole team **should have** | 本文 |
| **VP6C** | 主語＋他動詞＋動名詞 | **Testing** configurations／**Standardizing** tooling／have started **disabling** | 本文／出題文 |
| **VP7A** | 主語＋他動詞＋to不定詞 | Claude Code **fails to run** the linter | 出題文 |
| **VP9** | 主語＋他動詞＋that節 | developers **report that** ... | 出題文 |
| **VP17A** | 主語＋他動詞＋名詞＋to不定詞 | **Require** all developers **to install** ... | 出題文 |
| **VP18B** | 主語＋他動詞＋名詞＋原形不定詞（使役 have） | **have** each developer **configure** it | 出題文 |
| **[1] 単純現在時制** | Simple Present（He writes） | is／want／use／have／shares／adds／report | 本文・出題文 |
| **[5] 現在完了時制** | Present Perfect（He has written） | two **have started** disabling | 出題文 |
| **受動態＋法助動詞** | must / can't ＋ be ＋ 過去分詞 | **must be enforced**／**can't be overridden** | 本文 |
| **接触節（関係代名詞の省略）** | 目的格の関係代名詞が落ちる | preferences [that] you want／plugins [that] you use／Plugins [that] the whole team should have | 本文 |

## 今日の型に関する気づき

**接触節が3つ連続する（本日最大の構造的特徴）**：`Personal preferences you want everywhere` / `Tools and plugins you use across all projects` / `Plugins the whole team should have`。いずれも**目的格の関係代名詞 that が省略**された形。**want / use / have の後ろに目的語がない**のが手がかりで、これを見抜けないと「you want everywhere」が浮いて見える。箇条書きの中で連続するため、リズムとして掴んでおくと読みやすい。

**動名詞が箇条書きの項目そのものになる**：`Testing configurations before sharing with the team` / `Standardizing tooling across collaborators`。主語を持たず、動名詞句が名詞として機能する。さらに `before sharing` は**前置詞の目的語も動名詞**（× before to share）で、動名詞が入れ子になっている。

**使役の have（VP18B）**：`have each developer configure it`。to は付かない。let / make / have が同じ型を取る。8/1 の `Hooks let you run code`（let）に続いて、使役動詞の2例目。

**法助動詞と態が設計思想を映す**：Managed が `must` / `can't` ＋受動態、Project が `should`、Local が `won't`。**文法上の選択が、階層の強制力の差をそのまま表している**。技術文書を読むとき、助動詞に注目すると設計意図が読み取れる好例。

# スキル開発の記録（本日の作業）

## 新スキル question-archive v1.0 を作成

**目的**：english-parsing の【10】で生成した想定問題を、1問1ファイルで `questions/` フォルダに蓄積する。

**なぜ切り出したか**：想定問題は日次ログにも含まれるが、ログは1日分の学習全体を記録するため、**問題だけを探して解き直すことができない**。1問1ファイルにすれば、(1) 後日まとめて解き直せる、(2) 判断軸ごとに検索できる、(3) 出題の偏りを一覧で確認できる。

**起動トリガー**：「さきほどの想定問題を commit/push して」

**設計上の判断**：

| 判断 | 理由 |
|---|---|
| **解答を `<details>` タグで折りたたむ** | GitHub は `<details>` / `<summary>` を標準 HTML としてサポートしており、**JavaScript ではないためサニタイズされない**。解き直すとき、正解を見ずに選択肢まで読める |
| **`questions/README.md` に一覧表を置く** | 判断軸とドメインの分布が見える。特定の軸に偏っていたら次の作問で意識的に変えられる |
| **ファイル名を `question-YYYY-MM-DD-NN.md`** | 日付順に並び、同日複数問にも対応できる |
| **チャットに問題文を再掲しない** | 直前の応答で既に表示されているため。learning-asset v3.1〜v3.2 と同じ規律 |
